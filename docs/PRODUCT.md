# 产品定义

## 一句话定位

Architecture Block Studio 是面向代码系统的模块与接口设计工作台：用结构化设计连接“架构意图、AI 生成、代码理解与人工审查”。

它不是通用流程图，也不是源码编辑器。它把模块责任、公开端口、接口合同和内部层级建模为可验证对象，让一份设计既能被人阅读，也能被工具和 AI 稳定消费。

## 为什么需要它

AI 编程显著降低了实现成本，但没有降低架构决策的难度。相反，生成速度越快，以下问题越容易被放大：

- 局部实现正确，但同一业务事实出现多个 Owner。
- 新调用绕过公开接口，形成隐式耦合。
- 模块边界只存在于聊天或人的记忆里，无法持续审查。
- 代码和接口快速变化，设计文档停留在旧版本。
- Pull Request 文件很多，人只能逐行看 Diff，难以判断系统结构是否仍然成立。

本产品的价值不只发生在代码生成前，也覆盖生成后。它提供一层独立于具体语言和仓库布局的架构视图，让人可以设计、理解并审查代码系统。

## 产品北极星：Design / Understand / Review

### Design：先定义可实现的边界

用户在编码前建立模块、Owner、端口、接口方向与合同，回答：

- 模块为什么存在，拥有什么事实？
- 模块提供什么能力，明确不负责什么？
- 输入、输出、失败与依赖如何暴露？
- 内部结构如何通过明确端口与外部组合？

这份设计可进入版本控制，也可作为 AI 生成实现、拆分任务和编写测试的上下文。

### Understand：把代码结构变成可读系统

对于已有代码，人、脚本或 AI 可以把源码中的模块、公开接口和依赖事实映射为 `BlockDesignDocument`。Studio 通过层级展开、模块搜索、关联接口摘要、接口筛选、交叉定位和 Inspector 合同，把文件级细节提升为系统级理解。

当前版本负责展示、编辑与校验结构化结果，不直接扫描或逆向解析源码。源码分析器属于外部适配器；设计文档是它与工作台之间的公开契约。

### Review：让人审查架构，而不只审查文本

代码或 Pull Request 变化后，审查者可以检查：

- 新能力是否进入正确的 Owner 模块？
- 是否出现绕过端口的跨模块调用？
- 一个模块是否承担了多个独立变化原因？
- 接口方向、数据类型、失败行为是否与实现一致？
- 内部能力是否意外成为外部契约？
- 设计与实现是否发生漂移？

可视化审查不会替代逐行 Code Review、测试、静态分析或安全审计；它补充这些工具不擅长表达的模块边界与依赖关系。

## 目标用户

| 用户 | 核心任务 | Studio 提供的价值 |
| --- | --- | --- |
| 架构师 / Tech Lead | 定义模块边界、Owner 与依赖方向 | 把架构决策固化为可验证合同，而不是一次性图片 |
| 开发者 | 理解系统并在正确边界内实现 | 通过层级、端口和接口快速建立整体上下文 |
| Code Reviewer | 判断代码变更是否破坏结构 | 从模块和接口视角定位职责漂移与越界依赖 |
| AI 编程使用者 | 给生成过程提供稳定上下文 | 用结构化 JSON 约束生成、拆解和验收 |
| 工具 / Agent 作者 | 将源码或仓库分析结果可视化 | 通过公开 Schema 输出设计，不依赖 UI 内部实现 |

## 核心对象语言

- **Document**：一个可独立保存、加载、版本化的代码架构设计。
- **Level**：一个可视范围，拥有模块、连接和布局偏好。
- **Module**：有独立 Owner、责任边界和失败行为的结构单元。
- **Port**：模块对外公开的具名能力，拥有方向、侧边与可选数据类型。
- **Interface**：连接所引用的独立合同，拥有类型、Owner、协议与语义。
- **Connection**：某个 Level 内两个明确端口之间的方向性关系，可选保存人工调整的正交路由。
- **Hierarchy binding**：父模块端口与子设计内部端点之间的显式映射。
- **DRC issue**：从文档事实派生的结构或语义问题，不反向定义设计。

## 核心用户旅程

### 从零设计

1. 创建设计和入口 Level。
2. 添加模块，明确 Owner 与模块合同。
3. 添加公开端口，通过画布拖线或键盘端点选择建立同一类型化接口合同。
4. 对复杂模块创建子设计，显式绑定父子端口。
5. 运行 DRC，消除结构错误并评估语义警告。
6. 保存 JSON，交给开发者、AI 或评审者使用。

### 加载和理解已有设计

1. 打开本地 JSON、远程 URL 或启动链接。
2. 按标题、id、Owner 或 Level 搜索模块，从层级结果定位并原位展开内部结构。
3. 选中模块，按入站 / 出站摘要查看直接接口与对端。
4. 从关联摘要或接口浏览器进入连接，交叉定位画布与 Inspector。
5. 阅读 Owner、Purpose、Boundary、Failure 和源合同。
6. 将发现的问题反馈到代码或设计事实源。

### 审查一次代码变更

1. 由人或外部工具把变更后的结构同步到设计文档。
2. 对比受影响模块、端口与接口合同。
3. 使用 DRC 查找引用、方向、绑定和合同完整性问题。
4. 从模块关联摘要进入直接接口，沿接口追踪跨层依赖，在 Inspector 判断 Owner 与边界。
5. 形成“设计问题、实现问题或同步问题”的明确结论。

当前版本没有自动设计 Diff；变更对比是明确的后续产品能力，不能由临时 UI 状态替代。

## 体验原则

1. **画布保持安静**：模块和端口优先，线中不放标签；完整接口信息按选择渐进展开。
2. **选择即上下文**：层级树、接口列表、画布、DRC 和 Inspector 使用同一选择语义交叉定位。
3. **编辑不跳屏**：属性修改不重挂画布、不意外 Fit；布局和路由必须是显式命令。
4. **失败不破坏事实**：无效操作不产生半状态，无效加载不替换当前文档。
5. **复杂度按需展开**：父级上下文始终可见，内部结构仅在需要时展开。
6. **命令体系一致**：菜单、工具栏和快捷键应指向同一命令定义、可用性和反馈。
7. **审查证据可追踪**：任何警告、接口与模块都应能定位到文档对象和源码引用。
8. **专业而克制**：高信息密度、明确层级、统一 token，不用装饰性效果干扰结构判断。

## 产品边界

### 当前版本负责

- 本地单人模块与接口设计。
- `BlockDesignDocument v2` 的加载、编辑、校验、序列化与下载。
- 模块、端口、连接、接口合同和两级以上层级结构。
- Undo / Redo、dirty 状态、工作区面板和浏览器离开保护。
- 由文档派生的布局、正交路由、DRC、树、列表与 Inspector。

### 当前版本不负责

- 自动生成业务代码或替用户决定架构。
- 自动扫描、编译或逆向解析任意代码仓库。
- 证明代码实现与设计合同完全一致。
- 账号、服务端存储、多人实时协作与冲突合并。
- Draw.io XML 或任意通用画图格式兼容。
- 绕过浏览器权限原地覆盖任意本地文件。

### 演进方向

- 先完成编辑可靠性、Schema 兼容、恢复能力和大设计性能基线。
- 再完善审查工作流：设计 Diff、影响范围、问题筛选、源码定位与评审状态。
- 通过公开适配器接入源码分析或 AI 结构提取，不把语言解析混入工作台核心。
- 在单人文件模型稳定后，再评估协作、仓库集成和服务端能力。

## 成功标准

产品成功不以“能画图”衡量，而以以下结果衡量：

- 新用户能在没有额外指导的情况下完成第一条模块与接口设计。
- 日常用户的编辑不会因切换选择、布局、加载或保存而丢失事实。
- 审查者能从一条接口定位到两端模块、Owner、合同和层级路径。
- 大设计展开后仍然可读、可选择、可定位，不出现线标遮挡和不可解释的路径。
- 文件契约可版本化、可迁移、可回归验证，工具和 AI 可以稳定消费。
